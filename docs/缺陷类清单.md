# 缺陷类清单：哪些有门禁，哪些没有

写这个文件的原因：第 85 轮我以为「ImGui 不解析 markdown」这条已经有门禁，
去翻才发现**根本没有** —— 而第 84 轮我又犯了一次。

```
「我以为有门禁」和「有门禁」的差别，
要靠「故意犯一次，看抓不抓得到」才能发现。
```

清单本身不能代替门禁，但**清单能让「我以为有」这件事不再发生**：
每次修完一类 bug，就在这里确认它的门禁状态；没有门禁的，说明它只能靠
「下次审到那里时记得」，而这个「记得」已经失败过很多次。

---

## 已有门禁（`.ci/`）

| 门禁 | 覆盖的缺陷类 | 首次出现 |
|---|---|---|
| `check-ui-patterns.ps1` 规则 A | SameLine 跟在长度不受控的文本后面（值被顶出屏幕） | 22 |
| `check-ui-patterns.ps1` 规则 A2 | 相邻两行完全相同（重复插入） | 64 |
| `check-ui-patterns.ps1` 规则 B2 | 按路径写字段却没在函数内做值类型写回 | 68 |
| `check-ui-patterns.ps1` 规则 C | workflow 里 `run:`/`shell:` 缩进不对（CI 0 秒失败） | 49 |
| `check-ui-patterns.ps1` 规则 D | 渲染文本里的 `**`（ImGui 不解析 markdown） | 44 |
| `check-ui-patterns.ps1` 规则 E | 改游戏状态的调用被挂在面板可见性上 | 82 / 83 |
| `check-hosts.ps1` | 跨界面内容挂错宿主（功能消失且不报错） | 62 / 63 |
| `check-structure.ps1` | 花括号不配平（按行号搬代码时的结构性损坏） | 74 |
| `selftest-gates.ps1` | **每条门禁自己必须能红**，且**不该误报的必须不误报** | 65 |

`selftest-gates.ps1` 是这套体系的关键：它对每条门禁做两件事 ——
把该门禁要防的缺陷**原样注入**一次，确认它变红；再确认还原后变绿。
早期那批门禁（63 轮的 `$host`、64 轮的排除模式、85 轮的 markdown）
都是**写了很久才发现从来没生效过**。

## 没有门禁的缺陷类

下面每一类都**真实发生过**。它们只能靠「审到那里时记得」，而这个记得已经失败过。

| 缺陷类 | 发生轮次 | 为什么没做门禁 |
|---|---|---|
| **失败路径清掉了恢复所需的状态** | 78（句柄只置零不归还）、80（原字节无条件 clear） | 形状可描述但要区分「该保留的缓存」和「该清的缓存」，噪声大 |
| **用等价表示当身份** | 78（按 target+detail 找条目）、79（hookerMap 按地址索引） | 第 70 轮试过规则 D，收窄三轮后 15 处假阳性，**主动删掉**了 |
| **把容器 move 走、另一个组件还在读** | 82（`drawObjects`） | 需要跨文件数据流分析；规则 E 覆盖了最常见的一类 |
| **注释声称的机制代码没做** | 68、85 | `probe-comment-vs-code.ps1` 是探针：35 处命中、噪声太大，只用来缩小要读的面积 |
| **「拷贝不行」不等于「必须破坏源」** | 82 | 只能靠人读懂所有权语义 |
| **同一份数据在两处的解释不一致** | 82（次数 vs 曲线窗口） | 需要理解「这两个数字在描述同一件事吗」 |

## 维护约定

1. 修完一类 bug，如果**已经出现过两次以上**，问一句：能不能机械检查？
2. 能的，加门禁，并**立刻**往 `selftest-gates.ps1` 里加一条注入测试。
3. 加了门禁之后跑一次反向验证：**故意注入，确认变红；确认还原后变绿。**
4. 收窄三轮还是压不下误报的，**删掉规则**，并在这里写明为什么删
   （第 70 轮的规则 D 就是这么处理的）—— 误报多的门禁会被调低、然后被删掉，
   那比没有更糟。
5. 本文件里的「首次出现」列如果和实际不符，以实际为准并顺手改掉：
   **一个会过期的清单，也需要有人维护。**
