# 缺陷类清单：哪些有门禁，哪些没有

写这个文件的原因：第 85 轮我以为「ImGui 不解析 markdown」这条已经有门禁，
去翻才发现**根本没有** —— 而第 84 轮我又犯了一次。

```
「我以为有门禁」和「有门禁」的差别，
要靠「故意犯一次，看抓不抓得到」才能发现。
```

清单本身不能代替门禁，但**清单能让「我以为有」这件事不再发生**：
每次修完一类 bug，就在这里确认它的门禁状态；没有门禁的，说明它只能靠
「下次审到那里时记得」，而这个「记得」已经失败过很多次。

## 没有门禁的缺陷类

下面每一类都**真实发生过**。它们只能靠「审到那里时记得」，而这个记得已经失败过。
（原来有 6 类；第 87 轮关掉了「游戏状态挂在面板上」，第 88 轮关掉了「失败清掉恢复数据」，剩 5 类。）

| 缺陷类 | 发生轮次 | 为什么没做门禁 |
|---|---|---|
| **失败路径清掉了恢复所需的状态** | 78（句柄只置零不归还）、80（原字节无条件 clear） | 形状可描述但要区分「该保留的缓存」和「该清的缓存」，噪声大 |
| **用等价表示当身份** | 78（按 target+detail 找条目）、79（hookerMap 按地址索引） | 第 70 轮试过规则 D，收窄三轮后 15 处假阳性，**主动删掉**了 |

## 维护约定

1. 修完一类 bug，如果**已经出现过两次以上**，问一句：能不能机械检查？
2. 能的，加门禁，并**立刻**往 `selftest-gates.ps1` 里加一条注入测试。
3. 加了门禁之后跑一次反向验证：**故意注入，确认变红；确认还原后变绿。**
4. 收窄三轮还是压不下误报的，**删掉规则**，并在这里写明为什么删
   （第 70 轮的规则 D 就是这么处理的）—— 误报多的门禁会被调低、然后被删掉，
   那比没有更糟。
5. 本文件里的「首次出现」列如果和实际不符，以实际为准并顺手改掉：
   **一个会过期的清单，也需要有人维护。**

## 第 106 轮的一个否定结论（值得留着）

扫了所有声称「绝不能 / 必须检查 / 不能直接」的不变量注释，逐个核对
**代码里到底有没有对应的守卫**：

| 位置 | 声称 | 实际 |
|---|---|---|
| `Il2cpp.cpp:459` | 必须检查文件是否真的打开 | 有 |
| `Il2cpp.cpp:1688` | 回调绝不能让异常穿出去 | 有 try/catch |
| `ObjectDrawManager.cpp:1125` | 不能直接搬句柄（会 double free） | 确实重新加根了 |
| `Tool.cpp:174` | 采样绝不能放进 hook 回调 | 确实在渲染线程、且持锁 |
| `ClassesTab.cpp:4849` | 不能直接 return | 正确地没有 return |

**全部落实。** 这和第 68/85 轮（注释声称的机制根本没实现）不同 ——
所以「注释声称了机制」本身**不是**一个可靠的怀疑方向，
真正的问题是**注释描述的是哪个时点的世界**（见下）。

## 第 106 轮找到的另一类：修好了的 bug 留下**描述旧世界**的注释

第 83 轮把冻结循环从 `DrawWatches` 搬到了 `ApplyFreezes`。
那段解释「为什么不能待在 DrawWatches 里」的注释**留在了原地**，
于是它挂在了 `PatchStats` 头上。

同一文件里还有另一段：`frozenInvalid` 的说明写的是
「CollapsingHeader 收起时冻结循环没跑」—— 那是**第 83 轮之前**的世界，
第 83 轮之后那件事已经不可能发生了。

两段注释**互相矛盾**，而每一段单独看都挺合理。
只有把两个地方并排读才会发现。

> 这一类的特征：**注释本身没有错，是它描述的世界过期了。**
> 扫描方向应该是「这段注释在描述第几轮的世界」，而不是「这段注释说的是不是真的」。
## 第 107 轮：**试过但决定不做**的一条规则

第 106 轮那类「注释被留下的旧函数和它描述的对象分开了」看起来可以机械化：

> 一个函数上方的注释块提到了某个函数名，而那个函数名在该函数体里
> **一次都没出现** → 报。

把它当成 `docs` 里那条「注释声称的机制代码没做」，一起评估。
第 107 轮实测（把第 106 轮那个真实孤儿注回去，确认能抓到 —— **能**），
然后看它会误报谁：

| 位置 | 报的 | 实际 |
|---|---|---|
| `ClassesTab.cpp` ApplyFreezes | 提到 `CollapsingHeader` | **合法** —— 那段正是在解释「我不在 CollapsingHeader 里面」 |
| `ChangeLog.cpp` DropOldestLocked | 提到 `Clear()` | **合法** —— 「整张表被 Clear() 时同理」，在讲另一个函数 |
| `ObjectDrawManager.cpp` ResolveGameObject | 提到 `GetHandleTarget` | **合法** —— 并列的另一个函数 |
| `ObjectDrawManager.cpp` | 提到 `Initialize` | **合法** |

**4 个误报 : 1 个真报。**

**决定不加。** 这和第 70 轮删掉规则 D 是同一个决定：
一条会误报的规则，两轮之内必然被人加白名单，然后彻底没用了 ——
那时候它比没有更糟，因为它给了一种「这里有检查」的错觉。

> 误报率这么高的根因很具体：注释**合法地提到别的函数**是极常见的
> 写法（讲对比、讲并列，讲「我不是在 X 里面」）。
> 机械规则区分不了「孤儿注释」和「正常地提到兄弟函数」。
> 这类东西只能靠人读，而人读一遍就能看出来 ——
> 所以**不值得**为它写一条每次都要调的门禁。
## 第 109 轮：**发现了但决定不发货**的一个门禁改进

自检脚本 `selftest-gates.ps1` 会**真的去改源码**（注入违规再还原）。
`try/finally` 能保证正常路径和抛异常的路径都还原，但保证不了
**进程被杀掉** —— finally 根本不会执行。

第 109 轮就撞上了：自检跑到一半被打断，K 那条测试刚把
`.ci/check-ui-patterns.ps1` 的 `$dirs` 里的 `Il2cpp` 删掉，进程就没了。
那个文件留在被注入的状态，而且因为最后一项带了尾逗号，
它变成了**语法错误** —— 之后每一条门禁都跑不起来，
满屏红字里根本看不出「哦，这是自检留下的」。

试过的修法：动之前把原文备份到 `.ci/.selftest-backup/`，
脚本开头发现有残留就还原并大声报。**原型是通的**
（模拟一次「上次崩了」，文件被逐字节还原，hash 对上）。

但**没有发货**，因为它自己在测试中把树搞得更乱了 ——
而一个自己都还没跑绿的门禁改进，发出去比不发更糟：

- 备份文件里**不能混进别的东西**。我第一版往同一个文件里先写
  目标路径、再 `Copy-Item` 覆盖（路径想存在文件里），
  结果还原时把「源文件的内容」当成了路径。改成**路径编码在文件名里**。
- 中途我把 `Test-Rule` 里的 `$beforeBytes` 赋值整个替换成了 hash 统计
  （本意是「并排加一个」），而还原正是靠 `$beforeBytes` ——
  于是**每一条**测试都把文件写坏。一片红里真正的原因只有那一个。
- 加上「还原必须被验证」之后，诊断确实好了很多
  （能把「还原失败」和「规则没抓到」分开），
  但我没能把它稳定跑到全绿。

> 结论记在这里，是为了**下一个人不用再从头试一遍**。
> 真正的修法方向已经清楚：**自检不该改真实源码** ——
> 应该复制到一个临时目录里改，改完就删。
> 现在这套「就地注入 + 就地还原」在正常情况下是对的（21 条都验过），
> 唯一的缺口是「进程被杀」。
## 第 110 轮：又一次「从写下来起就是死的」检查

规则 N 的后半段（进托管代码的 `invoke` / `invoke_static` 必须有边界），
写完之后第一次跑是**绿的**，看起来没问题。

其实它**一条都没匹配上**。规则本体要求函数定义的 `{` 和签名在**同一行**：

    if ($t -notmatch '\{\s*$') { continue }

而 `MethodInfo::invoke` 的定义长这样：

    T MethodInfo::invoke(Il2CppObject *instance)
    {

`{` 在**下一行** → `continue` → 永远不检查 → 显示为「通过」。

> 这是第 64 轮那个教训的**第七次**：
> **一个从不失败的检查，和没有检查，在输出上无法区分。**
> 唯一的区分办法是「故意制造违规，看它抓不抓得到」。

这轮抓到了，是因为**做了反向验证**。如果只跑「检查通过」就提交，
就会往仓库里塞一条永远为真的规则 —— 而它给人一种「这里有检查」的错觉，
比没有更糟。

顺带记一条：这条规则抓到的**第一个**违规，就是我同一轮刚补上的
`invoke(Il2CppObject *)` 那个重载。也就是说，**先写规则再改代码**
的话，它会当场把漏掉的那个重载点出来。
## 第 112 轮：日志函数会抛 —— 把我前两轮的修复变成了「更糟」

第 110/111 轮给 `get_touchCount`、`hookerHandler`、`MethodInfo::invoke*`
都加了异常边界，`catch` 块里都调 `LOGE(...)`。

而 `LOGE` 展开就是 `logger::AddLog(...)`，`AddLog` 里是：

    new char[modifiedFmtLength + 2];       // bad_alloc
    Buf.appendfv(...)                      // 内部要分配
    LineOffsets.push_back(...)             // bad_alloc
    TrimLocked() 里的 std::string tail     // bad_alloc

**在 catch 里抛 = 边展开边抛 = std::terminate。**

也就是说：为了「异常不弄崩游戏」而加的 catch，如果自己打日志时内存不够，
会**比不加 catch 更糟** —— 直接 terminate，而不加的时候只是抛出去而已。

日志是**最后一道**防线，它自己不能再是第一个崩的地方。
七个函数全部包了边界（`AddLog` / `Clear` / `DroppedLines` / `ErrorCount` /
`CopyText` / `Draw` / `TrimLocked`）。

`TrimLocked` 的 catch 有一处特别要注意：它是被 `AddLog` **在锁内**调用的，
所以 catch 里绝不能再 lock —— 那是同一把非递归互斥量，第二次 lock 直接死锁。

规则 O：`Includes/Logger.cpp` 里每个函数体都必须有边界。

## 这条规则写出来之后，连撞两次「假绿」

1. 先把 `{` 要求在函数定义那一行 —— 这个项目里大多数函数是
   `{` 单独占一行，于是**一条都没匹配上**，显示为「通过」。
2. 修完又先把行 `Trim()` 掉再要求 `^ {4}` —— trim 掉的正是那 4 个空格，
   同样**一条都没匹配上**，还是「通过」。

两次都是「看起来是绿的」。第 64 轮的教训第**八**次、第**九**次重演。

> 现在这个项目里凡是按缩进/花括号找函数体的规则，都必须处理
> 「`{` 在下一行」和「先 trim 再数缩进」这两个坑。
> 已经踩了三次（规则 N 后半段、规则 O 两次）。
## 第 113 轮：第 33 轮那个族，全项目**清零**了

「返回指针的函数，其调用点没有判空就解引用」——
第 33 轮立这条时命中率是 33%，是这个项目产出最高的缺陷族。

第 101 轮把 Il2cpp（5009 行）解封进扫描范围之后，这轮第一次能对它做
全量重扫。做法：先把所有「返回裸指针」的函数名收集起来
（117 个），再用一条正则找「调用结果后面直接跟 `->` 或 `[`」的行，
再逐个核对前面三行有没有判空。

**命中 0。**

两个顺带确认的否定结论：

一、第 110 轮给 `MethodInfo::invoke*` 加的边界**没有**削弱方法页的
   「抛出异常」报告。那个面板走的是 `RuntimeInvokeConvertArgs(..., &managedException)`
   这条带异常出参的路，不是 `invoke*`；唯一一处 `invoke_method`
   （枚举 ToString）判了空，而且空值分支本来就会如实报「取不到 ToString」。

二、`unity/Il2cpp` 里的 GC 句柄层、字符串转换、字段读写，
   在前几轮逐个确认过有守卫之后，这轮也没有新命中。
## 第 115 轮：我说「这里有 bug」，然后发现自己看漏了外层作用域

第 114 轮加的趋势图用的是字面量 ID `"##spark"`，而**每一行**都是同一个
字面量。看上去就是典型的「控件 ID 冲突」。

我按第 101 轮的办法问「这个 bug 还可能长成什么别的样子」，扫出另外两处
同样形状的候选（`BeginPopupContextItem("##watchcopy")`、
`ColorButton("##color")`），然后动手加了一层 `PushID(i)`，
并写了一大段很笃定的解释：「ImGui 表格里控件 ID 由表 ID + 列 ID 算出，
不含行号，于是每一行的图共用同一个 ID，悬停提示会串」。

**然后我发现行循环的开头早就有了 `ImGui::PushID(static_cast<int>(i))`**
（BeginTable 之前）。整行被圈进独立作用域，所以每一行的 `"##spark"`
本来就是不同的。另外两处也一样：
ChangeLog 第 510 行、ObjectDrawManager 第 1679 行都有配对的 PushID/PopID。

多加的那层不会出错（只是 ID 层级深一层），但连同那段**错误的原因说明**
一起撤掉了 —— 一条把不存在的原因写得很笃定的注释，比没有注释更糟：
下一个人会照着它去找一个找不到的 bug。

> 教训：**说「这里有 bug」之前，先把外层的作用域读完。**
> 控件 ID 是有层级的（PushID → 窗口 → 表格列 → 字面量），
> 只看字面量就下结论，一定得出「ID 冲突」的误判。
>
> 这和第 111 轮那条「先写规则、再改代码」是同一个道理的两面：
> **先确认缺陷真实存在，再动手。** 上一轮是怕漏，这一轮是怕造。
## 第 117 轮：同一份状态词写两遍

自检页加「复制报告」时发现：表格里画的「通过/警告/失败/信息」是
switch 里四个字面量，复制出来的报告如果另写一份字面量，
两份会**漂移** —— 改了界面忘了改报告，或者反过来。

而读报告的人**无从判断哪边是真的**：他看到的「失败」在界面上
可能叫「警告」。所以抽出 `StatusLabel()` 作为唯一来源，
表格和报告都走它。

这个类在这个项目里本来就存在，改动记录页的 `KindLabel`
**一直是对的**（`ExportText` 复用了它），自检页是那个例外。
> 同一份文字被用在**两个出口**上时（界面 / 导出），它就该是一个函数，
> 不是两处字面量。凡是「导出」功能，都回头看一眼标签是不是复用的。
## 第 122 轮：PowerShell 的反引号 + `a = BEL 字符（0x07）

这轮改 `ClassesTab.cpp` 的时候，我在双引号字符串里写了：

    "// `arrayParams` 里存的就是这个裸指针"

PowerShell 里 `` `a `` **是转义序列**（BEL / alert），
双引号字符串里它被吃掉了，留下一个 0x07 控制字符：

    0x07 + "rrayParams"     而不是我想要的 "`arrayParams"

三个控制字符进了 C++ 注释。后果是连锁的：

    源码编码门禁        红（它也查控制字符，不只查 U+FFFD）
    K 扫描范围自检      报「还原后绿=False」  ← 纯属被牵连
    门禁自检            红
    check-all           红

> **K 的失败根本和 K 无关** —— 这已经是第 114、120 轮记过的同一条规律，
> 第三次验证：下游检查的红色经常是上游某个小毛刺的投影，
> **先去看最早失败的那条**。

更要记下来的是我自己的**修法也有坑**：我写了个修复脚本去匹配
`^\s*rayParams`，而实际文本是 `0x07 + rrayParams`（**多一个 r**），
所以正则没匹配上，脚本**静默什么都没做**，我却以为修好了。

## 第 133 轮：审我自己最近写的代码，抓到一个 relaxed 交接标志

第 94/97/102/103/112/123 轮都用了同一个方法 —— **审自己刚写的代码**。
这轮用的是第 121 轮那个 `BulkResult`，一个**跨线程交接**：

    done.store(true, relaxed)     工作线程
    done.load(relaxed)            界面线程 -> 接着读 ok / failed

relaxed **不建立 happens-before**。不同原子对象的操作之间没有顺序保证，
而本项目就是 **arm64**（弱内存序）—— 界面线程完全可能先看到
`done==true`、却读到**还没更新**的 `ok`/`failed`。

后果不是崩溃，是**给用户看一个假数**：
「成功 0 个，失败 0 个」，而实际上有 12 个成功。
讽刺的是这正是第 121 轮要消灭的那类问题 ——
界面上一个看起来很权威、实际不对的数字。

改成 release / acquire 配对。`Add()` 里的 fetch_add 保持 relaxed
（它们靠这对 release/acquire 定序），`Begin()` 和 `Report()` 末尾
那个 `store(false)` 是界面线程自己写的，保持 relaxed。

### 顺带一个干净的负面结论

`Dump().cancelRequested` 也是 `store(true, relaxed)`，
但它是**对的**：它只是个「请停下」的单向信号，
别的数据**不靠它发布**，工作线程轮询它、最终会看到就够了。
relaxed 原子量按标准保证每个对象自身的修改顺序和最终可见。

> 同一个 `relaxed`，两种用法，一种错一种对。
> 区别不在写法，在**这个标志盖着哪些数据** —— 那没法静态推出来，
> 所以规则只能按名字区分，并且必须记下这条理由。

规则 Y：`done` / `ready` / `finished` / `completed` 这类**交接标志**
不许 relaxed；`cancel` / `stop` 这类**请求标志**不管。
自检两条：一条验交接标志改回 relaxed 会红，
一条验请求标志 relaxed **不会**被误报（`-ExpectRed $false`）。
只验「能红」的门禁会把正确的写法也一起改掉。

## 第 137 轮：一个**结论正确、理由没写下来**的跨线程约定

继续审自己写的代码。这轮看第 116~120 轮那个后台筛选线程
（它是这个项目里唯一一处真正的 mutex + condition_variable 交接）。

`GetFilterFailure()` 是这样把失败原因交出去的：

    std::lock_guard guard(filterState->mutex);
    return filterState->failure;        // const char *

加锁只保护了**读指针**这一步；调用方拿到指针之后锁就放了，
而工作线程随时可能在同一把锁下改写它。

**现在恰好没问题** —— 机械核过全部三处赋值：

    failure = "无法 attach 到 il2cpp VM（...）"    字面量
    failure = "筛选时发生异常"                      字面量
    failure = "筛选时发生未知异常"                  字面量

全是**字符串字面量**（静态存储期），指针的值永远有效。

所以这不是 bug，是「**结论正确、理由没写下来**」：
下一个人把某处改成 `someStdString.c_str()` 就静默变成野指针，
而**编译器一句都不会说**，clang-tidy 也不会报。

> 这正是第 134 轮那个教训的**另一半**：
> 那里是「靠一个说不清的**时序**成立」，这里是「靠一个没写下来的**约定**成立」。
> 两种「现在没事」都需要被钉住，否则都会在没人注意的时候变成事故。

规则 AC：跨线程发布的失败原因只能赋**字符串字面量**。
（转发局部变量 `st->failure = failure;` 是允许的 —— 那个局部变量的
所有赋值处都受这条规则管。）

### 这条规则自己也踩了两次

2. 改成也查局部变量之后，它把 `rootFailures = it->second;`（一个 `size_t`）
   也报了 —— 那不是消息，是个计数。于是加了**类型**判据：
   先扫出全文所有 `char *` 声明，只对这些名字生效。

> 名字匹配用来**定位**，类型匹配用来**定性**。
> 第 111/125 轮那条「多要求规则里每个要求都要能单独红」在这里也一样：
> 只有一种判据的规则必然在另一侧误报或漏报。
## 第 138 轮：把「靠调用方小心」换成「类型上就不可能出错」

第 137 轮把 `GetFilterFailure()` 那个裸指针钉住了（规则 AC 管赋值那一侧）。
但真正根治的做法不是「记得别改」，而是**让类型本身不允许出错**：

    const char *GetFilterFailure();     ->     std::string GetFilterFailure();

原因很实在：裸指针版本的正确性**完全取决于每个调用方都在同一句表达式里用掉它**。
现在只有一个调用方符合这个前提（`ImGui::TextColored(..., filterFailure)`），
下一个就不一定了 —— 而它是**唯一一个**把后台线程的内存递出去的地方。

顺带确认了一个**相反**的写法是对的，别去改它：

    static std::unordered_map<Il2CppClass *, std::string> g_pendingScanErrors;
    ...
    g_pendingScanErrors[klass] = e.what();      // e.what() 是被**拷贝**进去的

值语义，锁内拷贝，调用方拿到的和自己的后台线程彻底无关。
（第 124 轮那个加根失败的 map 也是同一形状。）
**同样是「跨线程传消息」，一个是裸指针一个是 string —— 必须逐个看，不能按类名推断。**

> 一条抓得住不代表另一条抓得住。

## 第 139 轮：「静默失败」，以及门禁自己被 kill 之后留下的垃圾

### 一、产品侧的 bug：线程没起来，界面什么都不说

`SpawnDetached(任务名, 干活, 失败回调)` 的第三个参数，是 `std::thread`
构造抛异常（资源耗尽）时才被调用的。四个调用点里有两处只做了状态复位：

    [processingFlag]() { *processingFlag = false; }

于是界面上「恢复全部」的按钮恢复正常、进度条消失、**什么异常都没有**，
而实际效果是「一个方法都没恢复」。用户会以为是自己点的时机不对，
或者以为「本来就没有要恢复的东西」，于是**再点一次**。

> 「静默什么都没发生」比报错更难查：报错至少有个人会去看日志。

改成 `[this, processingFlag]()` + 复位 `processing/maxProgress/progress`
+ `g_bulkResult.Begin/Finish()`（0 个成功 -> 「成功 0 个，失败 0 个」）+ `LOGE`。

新增**规则 AD**：无参失败回调的函数体里，除了状态复位之外，
必须还有**界面读得到**的东西（`g_bulkResult` / `g_pendingXxx` / `LOGE`）。

规则 AD 自己第一版是**完全静默**的：我把捕获列表写成 `^\[\w+\]`，
而那两处的真身是 `[this, processingFlag]()` —— 一个都匹配不上。
**又是「存在 ≠ 生效」第 16 次**，靠「删干净了却不红」发现。改成
`^\[[\w\s,*&]+\]` 后双向验证通过。

### 二、门禁侧的 bug：自检改的是**真源码**，进程被 kill 就留在那儿

`selftest-gates.ps1` 的 `Test-Rule` 靠 `try/finally` 还原。
但 **`finally` 只在进程还活着的时候有用**。被 Ctrl+C、任务管理器、
CI 超时杀掉时，它一次都不跑 —— 文件就留在被改坏的状态。

这一轮真的中了一次：`check-all.ps1` 被中断时正停在规则 N 的注入阶段，
`ClassesTab.cpp` 里的 `try` 被换成了注释留了下来。
下一轮我打开文件看到「`try` 没了」，**还以为是自己上一轮写坏的**，
查了半天才发现是上一次运行的残留。

修法：**注入之前**先把原始字节另存到仓库外（`%TEMP%\il2cpp-selftest-stash-<路径>`），
下一次运行**在任何检查之前**先 `Repair-InjectedFiles` 写回去。
放在仓库外是因为备份文件本身会被门禁扫到；
不用哈希做后缀是因为跨进程就找不到上一次留下的备份（下面）。

这个机制写完之后，**三次都没生效**，全靠反向验证发现：

1. `[IO.Path]::GetHashCode` 在 PowerShell 里返回**空**
   （它不是静态属性，拿到的是方法组），目录名变成 `...stash-`。
   顺带一个更根本的问题：`String.GetHashCode()` 在 .NET Core 里
   **每个进程都不一样**（随机化，防哈希碰撞攻击）—— 而「跨进程」
   恰恰是这个机制的全部意义。改成用路径本身（把非法字符替掉）。
2. `Remove-Item $stash, $stash + '.path'` 被 PowerShell 解析成**三个**参数，
   每次报「A positional parameter cannot be found that accepts argument '+'」，
   备份永远删不掉 —— 于是「每次运行都以为上一次被中断过」。
   这和第 122 轮那个「反引号 + `a` 是 BEL 字符」是同一类：
   **少一个括号，命令就从「删两个文件」变成「报错 + 什么也没删」。**
3. 最阴的一个：`if ($cur.Length -ne $bakBytes.Length) { continue }`。
   我写它是为了省掉逐字节比较，结果**注入几乎总是会改行长**，
   于是这一条 skip 把整个机制废掉了 —— 正是第 111/125 轮那个形状：
   **一条为了省事加的守卫，恰好把「本该走的那条路」关上了。**

> 教训：**「没生效」的三种样子和「检查通过」在输出上完全一样。**
> 这次三处全靠「故意制造一次进程被杀，看它自己能不能爬起来」抓到。
> 而第 2 条那个括号，如果我不去数备份文件的数量，
> 它只会表现为「自检偶尔多打一行提示」—— 根本不会被当成故障。


## 第 140 轮：baseline 是 NDK 29 的产物，CI 却用 NDK 27 判它

起因是一行不该出现的数字：

    clang-tidy 告警: 46 条（baseline 50 条，新增 0 条）

上一轮 run 也是「46 条 / baseline 50 条」—— **代码不同，数字却一样**，
所以不是「4 条刚过期」，而是长期不一致。查下去：

    本地 D:\android-ndk-r29   Pkg.Revision = 29.0.14206865  -> 50 条，与 baseline 逐条对齐
    CI   ndk\27.3.13750724    Pkg.Revision = 27.3.13750724  -> 46 条

三处各说各话：README 声明 r29、baseline 是 r29 的产物、
**代码从来没在 r29 上编译过**（一直在 r27 上编）。

### 为什么这不只是「数字不好看」

判定逻辑是 `$new = $keys | Where-Object { $known -notcontains $_ }`，
而 r27 少报的那 4 条**都在 baseline 里**，所以 `$new` 为空，判「新增 0 条」，
放行。**从判据上说它没错**，错的是判据本身：

  - **反向漏检**。在 r27 上新引入的告警，如果恰好属于
    「r27 不报、r29 才报」那一类，门禁永远看不到它 ——
    「新增告警 = 失败」这条策略在两个版本之间**不等价**。
  - **差额被静默吞掉**。脚本只把两个数字打印在括号里，
    没有任何检查对「这个不等」提异议。

第 90~139 轮我一直以为「clang-tidy 门禁是绿的、覆盖了 88% 的代码」，
其中有一部分实际是**在 r27 上、拿 r29 的标准判**。
这是「存在 ≠ 生效」的第 18 种形态：**检查在跑，但跑的不是同一个东西。**

修：baseline 顶部写死 `NDK-TIDY: <rev>`，脚本核对，用错版本直接失败。
守卫放在**跑 clang-tidy 之前**（失败时零分析成本，
自检里要反复跑它）。CI 的 NDK 也从同一行读（`.ci/resolve-ndk.ps1`，
两个 job 共用一份——改一处漏另一处是第 138 轮的教训）。

### 顺带修掉一个我自己写的假绿

新加的 `NDK-TIDY:` 行**不以 `#` 开头**，于是被 baseline 加载器
当成了一条已知告警：报「baseline 51 条」、幽灵条目提示里还列出
「baseline 里有 1 条已经不触发了：NDK-TIDY: 29.0.14206865」——
看起来像「有条告警被修好了」，实际是元数据混进了告警集合。
声明行是元数据，不是告警。

## 第 140 轮之二：改 ci.yml 时留下重复 job，CI 照样绿

改 ci.yml 做 NDK 收口时，我大段替换算错了边界，旧内容**尾部没被吃掉**：

    - name: Pre-commit checks (single entry point)
      shell: pwsh
      run: .\.ci\check-all.ps1
      shell: pwsh          <-- 孤儿：上一项的兄弟节点残留
      run: .\build.ps1
    ...
  static-analysis:            <-- 整个 job 被复制了一份
    ...

两种结局都不可接受：

  - **孤儿 `run:`** 是语法错误，CI 在解析阶段就挂（还算好）
  - **重复 job** 在 YAML 里是「后者覆盖前者」—— 旧 job **静默消失**，
    CI 照样绿，而 `static-analysis` 可能就此不再跑

新门禁 `.ci/check-workflow.ps1` 查三件事：jobs key 唯一、
每个 `- name:` 块里恰好一个 `run:`/`uses:`、`- uses:` 块里不许有 `run:`。

### 这条检查自己也踩了两次

1. 第一版把 `- uses:` 型步骤也算进「必须有 run」，
   于是 checkout 那两步全被报成失败 —— **判据比事实粗**。
2. 修好后 job 收集器仍然漏：原写法用 `^\S` 判断「离开 jobs」，
   而 `jobs:` 后面**恰好有一段顶层缩进的说明注释**，收集器在那行就退出了，
   后面真正的 job 再也没被看到。于是我**注入的重复 job 它没报**。

第 2 条是我先怀疑检查器、查下去才发现的 —— 跟第 136 轮一样，
**规则把真问题判成「通过」是个信号，多半是规则本身有问题。**

顺带一条通用教训：反向验证「没报错」时，要先确认**注入本身是合法的**。
我第一次注入重复 job，把 `-replace` 的锚点放在注释块中间，
结果注入出来的 YAML 自己就不合法 —— 于是「没报红」既可能是规则失效，
也可能是注入无效，两者在输出上完全一样。

## 第 141 轮：两份从没被人读过的文件，一读就抓到两个

`Tool/Keyboard.cpp`（268 行）和 `Tool/ObjectDrawManager.cpp`（1708 行）
一直在 clang-tidy 的受检列表里，但**没人逐行读过** —— 第 133 轮开始的
「审自己写的代码」只覆盖了我自己新增的代码。

### 一、注释说要关掉旧键盘，代码只放了 GC 句柄

`Keyboard.cpp` 的 `Open()` 里：

    // 上一次还没关就先关掉，否则旧键盘对象会一直挂在触屏上，
    // 而且旧句柄泄漏。
    if (openedKeyboardHandle != 0)
    {
        Il2cpp::GC::FreeHandle(openedKeyboardHandle);   // <-- 只有这一句
        openedKeyboardHandle = 0;
    }

注释自己说的两个后果（「挂在触屏上」「句柄泄漏」），只解决了第二个。
`Destroy()` 在 `Reset()` 里是有的（`getMethod("Destroy")` + `invoke_static`），
唯独这条路径没走。TouchScreenKeyboard 背后是一个 OS 原生输入面板，
只放 GC 句柄只是让托管侧可被回收，**面板还在屏幕上**，
Unity 那边也认为它活着 —— 再开一个就是两个键盘。

改法直接调 `Reset()`，不抄一份逻辑：同一个语义有两份实现时，
**一定会只改一处**（第 138 轮 `GetFilterFailure` 就是这么漏的）。

### 二、`static` 把一次失败钉成了永久失败

    static MethodInfo *get_statusMethod = TouchScreenKeyboard->getMethod("get_status");
    if (!get_statusMethod) { LOGE(...); return Reset(); }

`static` 的初值**只算一次**。那一刻若 `getMethod` 返回 nullptr
（元数据还没注册完 / 这个 Unity 版本没这个方法），之后**永远**是 nullptr ——
每帧都走失败分支直接 `Reset()`。

于是**键盘永远打不开，界面上一点提示都没有**：用户看到「点了没反应」。
而同一个文件的 `Open()` 里专门写了「类解析失败可以重试」（第 50-57 行），
说明「暂时拿不到」在这份代码里**确实会发生**。

> 同一件事两处处理不同 = 必然有一处是错的。
> 这和第 134 轮（`methodCache[klass] = empty`）是**同一个形状**：
> 把一次暂时的失败缓存成了永久结果。

改法：不缓存（`get_text` 只在 `status==Done` 时查一次，是一次性事件，
慢路径完全够用）。

规则 AE：函数级 `static` 指针不许用「可能失败」的解析结果初始化。

### 规则 AE 自己又 inert 了一版

第一版的调用方正则只认 `A::b()`，而真身是
`TouchScreenKeyboard->getMethod(...)` —— 中间是 `->` 不是 `::`，
于是**一条都没匹配上**。注入真缺陷后它仍然报「通过」。

> 第 16 次「规则看着对、其实没在跑」。
> 这次和第 140 轮那条 workflow 检查连着 —— **连续两轮都是靠注入才发现**。
> 而注入之所以有效，恰恰是因为它不依赖规则里的任何假设：
> 我写完正则不检查它能不能匹配自己的目标行，只检查它能不能匹配**别人的**行。

## 第 142 轮：自检页报的那个版本号，是假的

141 轮都在修 bug，这轮回到目标的另一半：**功能完整性与体验**。

翻自检页时看到这一行：

    snprintf(buf, sizeof(buf), "v0.9 / %s 构建", __DATE__);

而全项目搜下来，版本号有**三个**说法：

    app/build.gradle   versionName "3.2"
    SelfCheck.cpp      自检页 "v0.9"
    仓库里还放着      Tool_v0.9.zip

Main.cpp 的窗口标题也是 `Il2CppTool v0.9 | HitMargin`。

### 为什么这个比看起来严重

自检页这一行的注释自己写着：

> 出问题时能一眼确认跑的是哪个版本，省掉一轮来回。

也就是说，它存在的**全部意义**就是「用户报『菜单没反应』时，
我据此判断他跑的是哪份代码」。而它报的是错的版本 ——
用户如实抄一份写着 v0.9 的报告过来，我按 v0.9 排查，
实际代码可能已经差了一百多轮。

> **一份自查报告里最关键的那一栏是假的，比没有这一栏更糟** ——
> 没有的话我会去问，假的会让我直接判断错方向。

而且 `CHANGELOG.md` 停在 v0.9，之后 140+ 轮的改动**一条都没记**，
所以用户拿到新版本时也看不到任何变化说明。

### 修法：版本号只有一个出处

`VERSION.txt`（仓库根）-> `build.ps1` 生成
`app/src/main/jni/Includes/Version.h`（生成物，在 .gitignore 里）-> 源码只读它。

比「在 .cpp 里写一个正确的常量」好在：**改完不重新编译就换不掉版本号**，
而「多个说法」的成因正是「有五个地方各写一份、改了一处」。

自检页现在报 `v0.142 (24de1e3) 构建于 2026-10-05`。
**提交号**比版本号有用 —— 版本号会被人遗忘，提交号不会，
而我真正需要确认的是「他跑的是不是和我手上同一份代码」。

规则 AF：源码里不许出现字面量版本号。

### 规则 AF 自己也漏了唯一那个真实案例

第一版加了「同一行出现 `IL2CPPTOOL_VERSION` 就放过」的豁免
（想排除生成物那一行）。而真实代码恰恰是：

    std::string(OBFUSCATE("Il2CppTool v0.9")) + IL2CPPTOOL_VERSION +

**同一行里两者都有。** 于是豁免把它放过了 ——
也就是说这条规则在我写它的那一刻，对**唯一**的真实案例是无效的。
手工注入验证时才发现（第 17 次「存在 ≠ 生效」）。

生成物已经按文件名排除了（`if ($f.Name -eq 'Version.h') { continue }`），
那层同行豁免本来就不需要。

### 顺带三件小事

1. 菜单标题必须**保持 OBFUSCATE**。我第一版直接 `std::string("Il2CppTool v")`，
   那是**行为退化** —— 这个项目系统性地混淆可见字符串（so 里 grep 得到
   `libil2cpp.so` 的话，静态分析就少了一层阻力）。
2. `OBFUSCATE` 的返回类型**不能直接参与 `+`**（只有 `operator char*`
   和 `operator std::string()`），必须显式 `std::string(...)`。
3. 改 `build.ps1` 时又丢了 BOM，于是中文注释被按 GBK 解码、
   `throw 'VERSION.txt 第一行为空'` 被截断成引号不配对 —— 报出来是
   `ParserError: UnexpectedToken`，看起来像语法错误，实际是编码。
   这是那条既有门禁要防的东西，第 140/141 轮我刚因为同类原因红过两次。

验证：改 `VERSION.txt` 为 9.9.9 -> 构建日志与 `Version.h` 都变成 9.9.9，
还原后一致。构建 rc=0。
