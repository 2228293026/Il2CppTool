#
#   cert-err33-c（约 55 处）
#       基本都是 `if (ImGui::BeginTabItem(...))` 这类 —— 界面控件的返回值
#       故意不用。逐个改成 `(void)` 或包一层纯属噪音。

#       `if ((currentlyOpened = ImGui::BeginTabItem(...)))` —— 记下这个

#   bugprone-narrowing-conversions
#       `size_t` -> `double`（printf 的 %zu/%.1f）、`ImGuiID` -> `int`。
#       全项目成片出现，改一遍是一次和本问题无关的大重构。
#   bugprone-empty-catch
#       两个都是**刻意的最后一道边界**，而且都在渲染路径上：
#         ChangeLog.cpp    记一条流水；注释写明「丢一条远比把渲染线程带崩好」
#         ClassesTab.cpp   FreeHandle 的兜底
#       把 catch 删掉会让这里**更容易**崩，不是更好。
#   cert-err58-cpp（poper 静态存储期初始化）
#       构造只存一个默认值、不分配 —— 现实里不会抛。
#       要动它得改这个全局对象的用法，是一次单独的改造。
#
# 换句话说：**抑制增加 21 条，换来覆盖率从 44.9% 到 88%**。
# 那是划算的 ——「没被看过的代码」比「已知的存量」危险得多。

# ---- 第 140 轮：这份 baseline 只对 NDK 29 成立（第 2 条门禁）----
#
# 下面每一行都是 **NDK 29 的 clang-tidy** 产生的。clang-tidy 的输出
# 随版本会变，而 `run-clang-tidy.ps1` 只比对「告警文本」，
# 不看版本 —— 于是用另一个 NDK 跑出来的结果照样能判「新增 0 条」：

#   CI   NDK 27.3  ->  46 条，**少 4 条**，仍显示「新增 0 条」
#
# 差 4 条本身不致命（27 不报 29 报的某些检查）。致命的是：
#
#  - **反向漏检**。在 NDK 27 上**新引入**的告警，如果恰好属于
#    27 不会报的那一类，门禁永远看不到它。「新增告警 = 失败」
#    这条策略在两个版本之间**不等价**，而 nobody 会发现。
#  - **差额被静默吞掉**。原来的脚本只打印
#    「告警 46 条（baseline 50 条，新增 0 条）」—— 两个数字不等，
#    却没有任何检查对**这个不等**提出异议。它只是被读者忽略了。
#
# 结论：**baseline 必须和 clang-tidy 的版本绑定**，否则它就是一份
# 不知道在哪个世界成立的清单。现在由 `NDK-TIDY:` 行声明生成它的版本，
# 脚本会核对，用错版本直接失败。
